# Unity CLI field notes

## Headless editor (default: the user keeps working)
- Start: `"<Unity Hub>\Editor\<version>\Editor\Unity.exe" -batchmode -projectPath <full path> -logFile Logs/claude/editor-headless.log -desiredWorkerCount 1 -standbyWorkerCount 0`, without `-quit`, via PowerShell `Start-Process -WindowStyle Hidden`. Started as a Bash background job it exited without reason after a while. Ready in ~10 s.
- **Own log file, always:** every editor launch (headless tests, builds, captures, the visible editor) gets `-logFile <project>/Logs/claude/<job>.log`; read logs only there. Without it the editor writes to the shared `%LOCALAPPDATA%/Unity/Editor/Editor.log`, which also belongs to any editor the user has open (2026-10-14: a Project A test run showed up in the user's own editor log). `unity test` has no log option (CLI 1.x): run tests with the Unity add-on's `docs/ai/araclar/testler.sh`, i.e. `Unity.exe -batchmode -runTests -projectPath <full path> -testPlatform EditMode|PlayMode -testResults <xml> -logFile <log>` (`-runTests` quits by itself; `-quit` would cut the run short), or `unity run <project> --log-file <log> --no-tail -- <editor args>`.
- **One import worker for small jobs** (bakes, prefab and mesh writes, tests): `-desiredWorkerCount 1 -standbyWorkerCount 0` override the project's Desired Import Worker Count and Standby Import Worker Count (default 2); images, models and audio import in worker processes of ~0.9 GB each. Project A 2026-10-16 (Unity 6000.3.17f1, a headless rebuild and bake): the default pool (5 workers, 25% of 20 logical cores) opened at once when the job rewrote a prefab and 17 meshes, 7.5-8.1 GB in all; with one worker 4.3-4.4 GB (the run's peak, 5.49 GB, came later in PlayMode), durations about the same (coast 3 s vs 3 s, occlusion bake 7 s vs 8 s, editor open with first imports 52 s vs 48 s). The workers opened although the project's Parallel Import setting read off, so pass the flags. Leave them out for first opens (empty `Library/`), package imports and platform switches: parallel import is faster there. `testler.sh` passes them (`IMPORT_WORKERS` raises the count); `unity run`: after `--`; `unity build`: `--args "…"` (builds unmeasured).
- `unity status` may not list it (CLI beta.11); beta.12 listed it as `ready` with its PID (Project B 2026-10-08). Not listed → check readiness with an `eval`. Close it with an eval calling `EditorApplication.Exit(0)` (after `AssetDatabase.SaveAssets()`); the eval then returns an error, as expected. Called inside `delayCall` it sometimes never ran.
- Works headless: `eval`/`eval_file`, opening scenes, Play mode (no focus rule, time runs, ~1000 fps), `recompile`, `run_tests`.
- No Game view; the screen counts as 640×480, so `ScreenCapture` is useless, and overlay canvases lay out at 640×480 (landscape) in Play; EventSystem raycast clicks still work. Captures with UI: **Screenshots** (URP: the RawImage path; an Overlay UI camera on the main camera's stack drew no UI).
- Open, change and save a scene in one call, then switch to an empty scene. Saving a scene left open after Play sessions wrote ~950 lines of layout and color overrides into a prefab instance (likely the 640×480 screen); open-and-save in one call once stayed clean (6 lines), but later a one-field change saved in one call wrote ~5,000 lines.
- Even in one call, adding a Canvas prefab to a scene wrote ~240 layout overrides into other UI prefab instances. Safe path, always for scenes with UI prefab instances: when the scene opens, store each outer prefab instance's `PrefabUtility.GetPropertyModifications`; before saving restore them with `SetPropertyModifications`; only the additions stay in the diff.
- Changing a few fields of a prefab variant with `LoadPrefabContents` + `SaveAsPrefabAsset` also wrote anchor overrides for slider fills in inactive submenus. Writing directly with `SerializedObject` on the asset's objects (`m_Enabled`, `m_IsActive`) + `SaveAssets` gave a clean diff.
- `Cursor.lockState` stays `None` headless (no window); cursor lock can't be tested in PlayMode tests → manual tests.
- A scene or prefab last saved before Unity 6.3 gets format-upgrade lines on its first save (Project B's GamePlay scene: ~330 lines: ParticleSystemRenderer v7 fields, TMP `m_TextWrappingMode`, LightmapSettings v13). Harmless; tell them apart from the real change when reading the diff.
- An idle headless editor uses ~1.4 CPU cores; close it before performance measurements.

## Status and connection
- `unity status --project-path .` may not find an open editor (`STATUS_NO_INSTANCES`); path-less `unity status` shows it as "ready". `recompile` and `command` work with `--project-path .`. Connection in doubt → `unity pipeline list`. Right after a script edit `recompile` can answer `COMMAND_FAILED` "Pipeline server returned 400 Bad Request" (the auto-refresh's domain reload): retry after ~10 s (Project B 2026-10-08).
- Another editor may also be open (another session's or the user's own): `unity status` then shows two instances. Pass `--project-path .` to every command so nothing reaches the other editor, and keep your own log file (Headless editor › Own log file).
- `unity open .` may not return until the editor closes, or may return 0 at once (with output redirected to a file): don't infer the editor's state from it; ask `unity status`.
- After adding or importing packages, main-thread commands such as `eval` may return "Main thread operation timed out after 5000ms" for a while in a background editor; retry at short intervals.
- Right after `AssetDatabase.Refresh` or a compile, `recompile`/`run_tests` may return "Network error", `result: null` or "Connection reset by server" (domain reload); retry after ~10 s.
- The first successful `unity recompile` after a compile error can return `failed=True errors=0` (stale flag); a second call gives `up_to_date failed=False`. Empty error list → ask once more.
- `unity recompile` once printed nothing (exit 0) from Bash and PowerShell; with `--json` it printed status, errors and warnings. Pass `--json` and read `data.status`, `data.errors`.

## Eval
- `unity command eval`/`eval_file` wraps the code in a method body: `using` directives don't compile ("Identifier expected"); use fully qualified names and return the result with `return`. Extension methods aren't visible: call them statically, e.g. `InputActionSetupExtensions.AddActionMap(asset, ...)`. `eval_file` takes `--file`.
- Editor not focused → Play-mode game time stops (`Application.runInBackground` off: frames run, `Time.time` doesn't advance). Before Play-mode evals set `Application.runInBackground = true` at runtime (Player Settings untouched). Builds behave the same: with Run In Background off an unfocused player pauses.
- An aborted PlayMode run can leave `runInBackground: 1` in `ProjectSettings.asset`; revert it. Set before Play has started (e.g. in the eval that sets `isPlaying = true`) it writes Player Settings at once: set it only once `isPlaying` is true (Project A 2026-10-07). Single-frame captures (e.g. Project A's LookDev) don't need it.
- After `AssetDatabase.CreateAsset`, `EditorSceneManager.OpenScene` in the same eval unloads unused assets: the reference turns fake-null and `{fileID: 0}` is saved silently through `SerializedObject`. Open the scene first, or reload the asset with `LoadAssetAtPath` after opening.
- A reopened editor can come up with an empty scene; open the scene with `EditorSceneManager.OpenScene` before Play-mode evals.
- Per-frame checks in Play (timing windows, jump height): register an `UnityEditor.EditorApplication.update` closure as a small state machine (act once per `Time.frameCount`), drive input fields directly (e.g. `StarterAssetsInputs.move/jump`), hand results to a later eval through a PlayerPrefs string, unregister at the end or when Play stops. A flat test floor far above the level keeps walls out of speed tests.
- A synchronous `wait_for` blocks for long; for timed captures (e.g. right after a death) use `on_met: {pause: true}`, then capture.
- An `EditorApplication.update` driver that throws keeps running and only logs to the editor log (`PipelineEval_*` in the stack): when a driver's samples go missing, look there first. (Project B 2026-10-03: a log line read a field that is null between two levels; the gap looked like a game stall.)
- If a game's pause menu owns the time scale (sets 0 every frame), disable that before changing time from an eval; a respawn may reset the scale to 1.
- Project settings without an API (Active Input Handling, Time): `SerializedObject` on `AssetDatabase.LoadAllAssetsAtPath("ProjectSettings/<file>.asset")[0]` → `ApplyModifiedPropertiesWithoutUndo` → `SaveAssets`. Unity 6 stores Fixed Timestep as a rational: set `Fixed Timestep.m_Count` over `m_Rate.m_Numerator` 141120000 (0.02 s = 2822400). `activeInputHandler` takes effect after an editor restart.

## Tests
- In an open headless editor `unity command run_tests --mode playmode` returns at once with "0/0 passed" (or "Total 0") while the run goes on behind it (2026-10-17: the editor log showed 8/8). Never read a PlayMode result from the command's answer: wait for a new `[TestResultCollector] Run finished` line in your own `-logFile`, then read `%USERPROFILE%/AppData/LocalLow/<companyName>/<productName>/TestResults.xml` (the folder moves when the product name changes); per class with `--filter <class> --async_tests true` (a project's script `docs/ai/araclar/playmode-sinif.sh`). EditMode's answer is right. The full suite with the editor closed: `bash docs/ai/araclar/testler.sh PlayMode`.
- Async runs: `test_status` returns "Connection reset by server" while the editor enters Play; a helper script that took that as "done" exited without results. Read `Temp/pipeline_test_status.json` (`status`, `summary`, `results`) and wait on that file.
- The editor may exit normally right after scene-loading smoke tests (editor log: "About to save layout" → "Pipeline Server stopped"; the next `recompile` gets "Dispatcher is shutting down"). After smoke tests check `unity status`; if it closed, continue with `testler.sh` (editor closed).
- With the test assembly not compiling, a PlayMode `run_tests` doesn't error: `test_status` stays "running" for minutes, and cancel or retry do the same. Read `unity recompile`'s result every time; the error showed only in an editor-closed run (then `unity test`: "Scripts have compiler errors"; `error CS` lines in the editor log; `testler.sh` prints them). Seen cause: Unity's NUnit has no `Assert.Multiple`.
- The `run_tests` filter is a case-insensitive substring match; `A|B` returns 0 tests; run filters separately.
- `unity command console` can miss logs written while leaving Play; check the editor's own `-logFile`.
- Maximum Allowed Timestep is 0.333 s: one slow editor frame can skip a 0.25 s phase. In short-phase PlayMode tests lower `Time.maximumDeltaTime` in SetUp and restore it in TearDown.
- With a real keyboard attached, `GetBindingDisplayString` names keys by the OS layout (AZERTY: `<Keyboard>/1` is "&"); never hard-code key names in tests, derive the expectation from the binding.

## Screenshots
- `unity command screenshot --view game|scene --output Logs/claude/screens/x.png` writes relative to the project root; prefer it. `capture_game_view --save_path` resolves under `Assets/` (the image is imported as an asset); for another camera it takes `source: camera` + `camera: <name>`.
- `screenshot --view game` draws only `Camera.main`; Screen Space Overlay UI is missing. In Play use an eval with `ScreenCapture.CaptureScreenshot(fullPath)` (written one frame later; not headless). Gizmos enabled in the Game view end up in the image (NavMesh gizmos tint walkable ground cyan even with nothing selected); turn off `UnityEditor.GameView`'s `drawGizmos` via reflection before the capture, restore it after.
- One overlay canvas (a panel, the HUD): switch it to Screen Space Camera on a temporary camera that renders into a 1920×1080 texture, wait a frame, `Render()`, `ReadPixels`, then switch back. Disable `SafeArea` components for the shot: they compare against the 640×480 headless screen and shrink the wrappers.
- Switching a canvas to Screen Space Camera: set `worldCamera` together with the mode (without its camera it reads back as Screen Space Overlay), then disable and re-enable its `CanvasScaler` (it sizes in `OnEnable`/`Update`) and call `Canvas.ForceUpdateCanvases()`, so it lays out at the camera's texture size. A camera without a target texture lays canvases out at the 640×480 screen and they don't show; on the main camera itself nearby objects drew over the HUD.
- World plus HUD in one image, URP (Project A's path): a disabled Base UI camera far below the world (culling UI only, post-processing and shadows off) renders into its own texture; the world camera renders into a second texture shown by a RawImage on a picture canvas behind everything (Screen Space Camera on the UI camera, `planeDistance` 10, sorting order −32000); HUD root canvases switch to Screen Space Camera on the UI camera (`planeDistance` 1). A few frames later render the world camera, then the UI camera, read the UI texture, switch the canvases back. One render, no alpha compositing. What failed in URP: an Overlay UI camera on the main camera's stack drew no UI (Project A 2026-10-02: `Camera.Render()` doesn't draw the stack; Project E 2026-10-12, URP 17.3), and the built-in path below (a second camera into the same texture lost the first image: URP draws through its own intermediate texture). (Scripts: Project A `tools/level/shots_capture.cs`, Project E `docs/ai/araclar/hud-akis.cs`.)
- World plus HUD in one image, built-in RP (no camera stack): move every active Screen Space Overlay root canvas to Screen Space Camera on a temporary camera (clear Depth, culling UI, a 1920×1080 render texture, `planeDistance` by sort order), disable `SafeArea`; one frame later render `Camera.main` into the texture, then the temporary camera, read the pixels, and switch the canvases back. (Project B's script: plan mayin-tarlasi-cekirdek, step 6.)
- Judge visual changes by comparing the pixels of two captures, not by eye (a 72% black overlay in linear color shows as ~55% on screen, 0.28^(1/2.2)).
- Headless, a skinned character can stand in its bind pose (T-pose) in a session's first shot: with Animator culling `CullUpdateTransforms` bones are written only after a frame in which a camera drew the renderer, and no camera draws on its own headless. Take a throwaway shot first (or set `AlwaysAnimate` for the shot) before judging poses.

## Packages
- From a background editor a package request once reached UPM only after ~7 min; `set_autotick` was on and `editor_focus` didn't bring the window forward. Package resolution takes ~90 s on this machine (also at startup); `hubIPCService` timeouts appear while Unity Hub is closed.
- Slow package operation: first look for the `add-dependency`/`remove-dependency` request in `%LOCALAPPDATA%/Unity/Editor/upm.log`. Don't send a second request: it gets 404 and leaves a Package Manager error in the console. If needed, ask the user to click the Unity window.
- Working path in a background editor: eval `Client.AddAndRemove(...)`, poll the result in an `EditorApplication.update` callback and write it to a file; installs finished in seconds (Localization + Addressables). A `Client.Add` that ended EPERM on the `Library/PackageCache` rename passed when sent again (Project C 2026-10-16): resend only after the first request completed.
- Ask the editor for versions: `Client.Search` → `versions.recommended`. The registry's "latest" may not be the one recommended for your Unity (Addressables 4.1.0 vs 2.9.1 on 6.3).
- `AssetDatabase.ImportPackage` silently ignored a `.unitypackage` re-packed with Python (no error, no log); Unity-made packages (TMP Essentials) imported fine. For part of a package, extract the files directly keeping GUIDs (Project A: `tools/unitypackage_extract.py`) and run `unity recompile`.
- Pipeline 0.8's `bake_navmesh_surfaces` doesn't bake NavMeshSurface (`not_implemented`): `surface.BuildNavMesh()` → `AssetDatabase.CreateAsset(surface.navMeshData, "<scene folder>/NavMesh-*.asset")` → save the scene.

## The player in the background (benchmarks)
- A batchmode player (even without `-nographics`) renders no cameras: off-screen rendering gave black frames and 0.35 ms. Use it for simulations, never for benchmarks.
- `SW_SHOWNOACTIVATE` doesn't stop Unity from taking focus (it held focus 1-4.5 s). For benchmarks run windowed and, once scripts load, push the window behind the user's windows and give focus back (Project A: `BackgroundWindow` with `-nsBackground`, plus `tools/bench_batch.py`); a window behind others still renders at full speed.
- Measurements fluctuate while the user works (one preset ranged 3.8-8.7 ms): run more rounds, report the median and the minimum.
- Check each run's logged resolution: saved settings can override `-screen-*` arguments; drop runs at a different resolution.
- Game-code allocations in the editor: the `ProfilerRecorder` counter "GC Allocated In Frame" includes the editor's own (~2 MB per frame headless), useless. Record with `UnityEditorInternal.ProfilerDriver.enabled = true` (`profileEditor = false`) for some frames, then read `ProfilerDriver.GetHierarchyFrameDataView(frame, 0, MergeSamplesWithTheSameName, columnGcMemory, false)`: the `PlayerLoop` item's GC column, and its allocating children by `GetItemPath`. Works headless (Project B 2026-10-03, 161 frames).
- Mono's `GC.GetAllocatedBytesForCurrentThread()` always returns 0 (tried in the editor). To see allocations in a build, count GCs in the measurement window; heap growth counts as allocation only if no GC ran in that window. TMP's numeric `SetText` doesn't allocate in builds (its string copy is inside `#if UNITY_EDITOR` in `TMP_Text.cs`).
