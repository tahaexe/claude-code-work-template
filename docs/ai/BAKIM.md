## Plan closure
1. **Verify:** check each acceptance criterion against evidence: tool output seen in this session (the error check and the eye check, PROTOKOL §4) or the comprehensive test stage's report; no test suite runs here (that stage runs them). A check that couldn't run or was never tried is "not assessed" in the report, never "passed". Non-automatable checks (e.g. game feel, on-device performance) go to manual tests.
2. **Review:** work players or viewers see (screens, feel, art, store pages, videos) → always: the area's expert agent reviews the result (with the step and eye-check screenshots; `tasarim/gorsel-stil.md` exists → visual consistency too), then an honest check against the plan's **Review** section: was it tried (UI, feel, smoothness), and how does it stand beside the best examples? Weak → fixed before it ships; the answer goes in **Result**. A plan whose comprehensive test stage already ran both (step 5 there) cites them here. Other plans (your call): worth it when the plan was risky (save data, purchases, ads, rewards and time, data migration) or long, and the project has a review agent for the area (e.g. `unity-uzmani` for Unity code): have it review the files the plan changed; ask only for bugs and requirement gaps. Small plan with a clean error check → no review; report "review: not needed". Serious findings → a fix plan (PROTOKOL §3), not fixes inside the closure. Follow-ups not fixed now → `hafiza/teknik-borc.md`.
3. **Result:** plan status `done`; in **Result** write what changed, known limits, recommendations.
4. **Move durable knowledge** (only what will matter later):
   - decisions not specific to the plan → `hafiza/kararlar.md`
   - pitfalls learned → `hafiza/dersler.md`
   - knowledge of a growing area → `hafiza/<topic>.md` (create if missing, add a line to `HAFIZA.md`)
5. **Manual tests:** copy the plan's manual tests into `manuel-testler.md` (Turkish) under the fitting area, tagged with the plan's short name; skip items already there.
6. **Archive:** move the plan index and its step folder to `planlar/arsiv/` (`git mv` if git).
7. **DURUM:** clear the active plan or move to the next approved plan/phase; add the finished plan to **Recently completed** as one line ≤150 characters (max 5; drop the oldest). A release plan also adds the post-release line to **Up next** ("After release" below).
8. **Tidy:** apply "Memory tidy-up" below only to memory files changed in this plan.
9. **Commit** (if git): `docs: close plan <short-name>`.
10. **Template update:** the template's PROTOKOL (folder: global CLAUDE.md) newer than line 2 here → run `KURULUM.md` → "Güncelleme (Update)" yourself now (it keeps the project's own CLAUDE.md lines, memory and plans); one line on what changed for this project goes into the report.
11. **Report** (Turkish): short summary, how many manual tests were added (the list is in `manuel-testler.md`), checks not assessed, review findings (if any) and the honest check's answer, CLAUDE.md rules added, the next task and `/clear` before a new task. If the project has `docs/ai/sablonlar/oyun/`, suggest the fitting doc: prototype report after a prototype plan, playtest report when a build goes to players, post-mortem after a major milestone.

Cancelled plan: status `cancelled`, reason in **Result**, archive, update DURUM.

## Comprehensive test stage (pre-release)
No tests while the steps run (PROTOKOL §4: the error check, the eye check at a plan's or phase's last building step). When everything is declared ready, every step is tested one by one, once and thorough: the penultimate step of a plan that delivers (before every release: store build, deploy; or work used as it is: a tool, a site change, a channel format), then the last step (release or delivery) and the closure. None in a prototype that won't ship (the error and eye checks are enough there) or in a plan whose work ships with a later release plan: its step files' **Final test** sections wait for that plan's stage.
1. **Matrix** (in the test step's file): one row per step file's **Final test**: this plan's, and those of the plans and phases closed since the last release whose work ships in this one (`planlar/arsiv/<plan>/`); a row without a pass bar gets one first. Before a release, also: every existing test suite once, the release checklist and the test list (`el-kitabi/yayin-oncesi-test-listesi.md` where installed: every level through the real controller, saves with a relaunch and an old save, the device matrix, purchases in the sandbox, test ads and consent, ad and navigation flows, rewards and the clock, analytics in DebugView, performance and memory, screens in both languages and localization, accessibility, real taps on every screen, the store build on an emulator, the store's pre-launch report); then the manual list.
2. **Run** cheap to expensive (the test list's order), one row at a time, on the build that will ship (same commit and settings); evidence per row (command and result, log excerpt or screenshot; a release's under `Logs/claude/release/<version>/`). Result: ✓ · ✗ → fixed → ✓ · manual (`manuel-testler.md`) · "not assessed: why".
3. **Red:** a bug is fixed before the release, then that row and its neighbours are tested again (rows the fix touched, the store build's smoke run); a stale or flaky test is updated, or disabled with its reason in `hafiza/teknik-borc.md`. Never delete or loosen a test or hard-code its result to hide a bug; unclear cause → stop and ask (PROTOKOL §4).
4. **New tests** only here, as many as needed, where a bug would cost players or money; a test for a fixed bug is seen failing without the fix first.
5. **Review and decision:** work players or viewers see → the area's expert agent reviews the report and the screenshots, then the honest check against the plan's **Review**. The report (rows with results and evidence, not assessed with why, accepted risks, decision: release or hold; the test list's report file in a release) → summary in the test step's file; the last step runs only on "release". Hold → the failing rows become fix steps before it.

## After release: measure, analyse, decide
A game or app released to a store is announced, then measured before new content is built on it.
1. **Announce the same day** a version goes live (store approval and release; a new game's first version too): the text in `store/duyuru/<version>.md`, Turkish and English: a title, a 1-2 sentence intro, 3-5 player-facing bullets (players' words, no technical terms), the store links, the cover image's path (a store screenshot or the press kit). Published on the studio site's news or devlog and on the community devlog (e.g. Oyun Günlüğü); with a session manager, under its rules (it may publish it).
2. **Measure from the first release:** version 1 already ships the measurement events: level start and end, session length, ad and purchase events, D1 and D7 by version (mobile with Firebase: `el-kitabi/firebase-olcum-ve-uzaktan-ayar.md`); crashes (Crashlytics, Android vitals) and store conversion come from the consoles. The gate (D1, D7, day-1 minutes; continue and grow thresholds) is set before the data arrives (game summary › Ölçüm hedefleri) and never moved after it.
3. **Window:** at least 14 days from the release going live without new content (levels, modes, maps, events); fixes, compliance and store-policy changes and review replies go on. The release plan's closure adds to **Up next**: "<version>: no new content until 14 days after it goes live, then the post-release analysis (`BAKIM.md` › After release)"; the date is filled in once the release is live.
4. **Analysis report** (Turkish; a session manager's analyst writes it where the machine has one, else this session): D1, D7 and day-1 minutes against the gate (a range on few installs; too few → "not enough data", the window grows), the level funnel (where players quit), session length, crashes, ad and IAP revenue, store conversion, ratings and review themes; at most 3 recommendations, each tied to a finding.
5. **Decision** (the user's): develop (a new version), maintenance (fixes only) or shelve; recorded in DURUM's **Up next** with its date, the reason and the report's path.
6. **Next version:** its plan starts from the analysis findings (the biggest drop fixed, what players like grown, revenue improved) plus a short pre-research of the relevant areas (`el-kitabi/on-arastirma.md`); both go into its **Review** section. After it goes live → steps 1 and 3 again.

## Memory tidy-up
- **Duplicates:** merge entries that say the same thing, entry by entry. Never rewrite a whole file as a summary.
- **Staleness:** check entries against the code; search the file/function names they mention. Fix or delete what is no longer true.
- **Unneeded:** delete what is easily derivable from code or git history, one-off, or no longer important.
- **Decisions:** don't delete a superseded decision at once; strike its title (`~~…~~`) and add "→ changed by YYYY-MM-DD decision". Delete very old, irrelevant ones.
- **Size:** check the limits with `LC_ALL=C.UTF-8 wc -m` (PROTOKOL §5; plain `wc -m` in Git Bash counts bytes). Move DURUM detail into plans or `hafiza/`, tech debt into `hafiza/teknik-borc.md`; split topic files by topic and index them. CLAUDE.md over its limit → trim it yourself: details to a `hafiza/` file with a one-line pointer; tell the user.
- **No fact loss:** after rewriting or moving entries, run `python docs/ai/araclar/kayip-kontrol.py --rev HEAD <changed files>`: restore every reported missing fact; for each listed clause make sure its reason, condition or exception survived (reworded is fine).
- **Index:** one line per memory file in `HAFIZA.md` (handbook entries share one line, each hint keeping the tasks of its `read_when`; never trim a hint to a topic name; an entry that CLAUDE.md or PROTOKOL already routes to gets no hint), paths relative to `docs/ai/`, with a correct "when to read" hint; delete lines and entries pointing to missing files.
- **Commit** (if git): `docs: tidy Claude memory`.
