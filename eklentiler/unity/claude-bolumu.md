## Unity
<!-- unity add-on v1.45 · from the template; "şablonu güncelle" refreshes it and keeps project-specific lines -->
- **Skill first:** for any Unity task use the fitting `unity:*` skill; name it in the step's **Tool** field (e.g. UI → `unity:ui`, packages → `unity:unity-package-management`).
- **Unity CLI first** (user's preference; `unity:unity-cli` skill): drive the editor (scenes, prefabs, assets, Play mode, C# eval), compile (`unity recompile`), test (open editor: `run_tests`; closed: `docs/ai/araclar/testler.sh`; never `unity test`, its editor writes the shared `Editor.log`), build (`unity build`); skills' MCP steps via the CLI too. Use Unity MCP where the CLI falls short, and say so. CLI or `com.unity.pipeline` missing → install (silently on the owner's computer per the global CLAUDE.md, else ask once). Pitfalls, headless editor: `docs/ai/el-kitabi/unity-cli-saha-notlari.md`; read before non-routine CLI work or when a command misbehaves.
- **Stay in the background:** the user keeps working: headless editor, background builds and test players (handbook); a window comes forward only if a test needs it, after telling the user.
- **No hand edits:** change scenes (`.unity`), prefabs, `.asset` and `.meta` files via Unity CLI; commit `.meta` with its asset; never hand-edit `Library/` or `Temp/`.
- **Verify:** C# changed → clean compile and related tests run (Commands table). Tests live under `Assets/` in their own `.asmdef` (Unity compiles only `Assets/`, `Packages/`). Start tests after compiling ends (mid-compile they can hang).
- **C# LSP** (`csharp-lsp` plugin): never `cd` into a subfolder (absolute paths, `git -C`), or every LSP call fails; pitfalls: `docs/ai/el-kitabi/csharp-lsp.md`.
- **Manual tests:** besides gameplay, feel and visuals add what fits: startup/crash, the changed mechanic, old-feature regressions, save/load, FPS drops.
- **Unity expert** (`unity-uzmani` agent): architecture opinion when planning; review at closure if needed.
- **Design docs:** templates in `docs/ai/sablonlar/oyun/`, filled in `docs/ai/tasarim/` (Turkish). Suggest the game summary for a new idea, the playtest report when a build goes to players, the release checklist before release.
- **Release:** Claude creates the versions on the game's stores (Play Console, App Store Connect, Steamworks; Claude in Chrome) with their data (version name, release notes in both languages, listing changes) as direct releases (production at 100%, App Store auto-release; no test tracks, TestFlight or phased rollout), sets the version numbers and builds into `Builds/` (Android signed AAB, iOS Xcode project, PC player), then stops: the user uploads the builds and sends them for review (Steam: sets the build live), never Claude. Signing: the user types the keystore passwords into the open editor's Publishing Settings and Claude builds there; passwords never go into a file, doc or command.
